# Выпуск SDK

Прочитай `AGENTS.md`; проверь наличие `docs/releasing.md`, сценариев GitHub Actions и описания выпуска, затем прочитай существующие материалы. Отсутствующие целевые файлы не считай готовыми. Сначала установи, разрешена ли подготовка, изменение настроек или фактическая публикация: план выпуска не даёт разрешения на внешнее действие. При продолжении частичного выпуска не превращай эту задачу в перенастройку уже достаточной инфраструктуры.

## Подготовка и GitHub

- Единица выпуска — фиксированные commit, версия, снимок контракта и проверенные артефакты четырёх пакетов. Обычный build и pull request не публикуют пакеты.
- Корневой Node-пакет приватный и никогда не публикуется. Реестры языков: npm, PyPI, crates.io; Go распространяется из публичного GitHub module.
- Перед сменой visibility проверь публикуемое содержимое и историю. Не скрывай найденные реальные секреты простым добавлением `.gitignore`; останови публикацию и согласуй конкретное восстановление. Автоматическое переписывание истории не входит в обычный выпуск.
- Сверяй настройки GitHub по API, сохраняй существующие организационные ограничения. Права сценариев GitHub Actions минимальны; непроверенный код pull request не получает секреты публикации. Не используй `pull_request_target` для исполнения кода внешнего PR.
- Зависимости Actions закрепляй commit SHA, генератор — версией и digest/checksum. Доверенная публикация через OIDC привязана к точным владельцу, репозиторию, сценарию и среде; `id-token: write` выдаётся только заданию публикации.
- Сначала создай и проверь реальные проверки CI, затем делай их обязательными в защите `main`. Не требуй несуществующий check. Не назначай фиктивного обязательного reviewer; используй подтверждённых владельцев.
- Используй учётные записи организации в реестрах, проверенные имена и права. Уточни действующие требования первой публикации; если OIDC требует предварительно созданного пакета, выполни только разрешённый первичное создание пакета с минимальными временными правами и задокументируй результат.

## Версии и исполнение

1. Сверь версию во всех описаниях пакетов с целевым выпуском и происхождением контрактов. `v0.x.y` — общий тег; Go в подпапке требует также `go/v0.x.y` на том же commit. С переходом Go на major 2 изменяется путь модуля.
2. Собери и проверь все артефакты до первой публикации. Установи их в чистые потребительские проекты; составь описание выпуска с контрольными суммами и происхождением. Не пересобирай другим commit после частичного успеха.
3. Выполни только разрешённые каналы, сохрани подтверждение каждого. Теги — тоже публичный эффект; не создавай их как часть обычной проверки.
4. После каждого канала проверь наличие версии и возможность подключения через настоящий реестр/proxy. Изменённое состояние не доказывается только успешным завершением CLI.
5. Сообщай частичный успех явно. После таймаута сначала прочитай состояние реестра; повторяй только отсутствующую публикацию тем же артефактом, если правила реестра это допускают. Если внешний результат остаётся неоднозначным, исходный артефакт недоступен или его контрольная сумма расходится, останови затронутую публикацию и зафиксируй недостающее свидетельство. Не запускай бесконечный опрос и не подменяй исходный commit новым состоянием `main`.
6. Ошибка опубликованного кода исправляется новой версией. Не переиспользуй имя/версию, не передвигай опубликованные теги и не обещай общий rollback реестров.

## Pine и завершение

- Pine исходники и примеры входят в GitHub Release как резервное хранение. Публикация импортируемой библиотеки в TradingView — отдельная ручная операция через Pine Editor, применяй `pine-signals`.
- Версию Pine-публикации и её соответствие commit фиксируй только после подтверждения. Не публикуй в README несуществующий путь импорта.
- Обнови руководство и описание выпуска, включая пропущенные каналы, внешние ограничения и безопасное продолжение. Не отмечай общий выпуск успешным, пока обязательные каналы не приняты и не проверены.
